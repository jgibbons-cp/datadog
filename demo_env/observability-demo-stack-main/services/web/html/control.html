How to drive this. Leave the storefront and the load generator running, flip one scenario at a time, then wait 30–60 seconds for the signal to land in Datadog. Every scenario below maps to a specific place in the product — the Where to look line tells you where to go.

Slow query — unsargable predicates

Wraps DATE() around an indexed timestamp column and switches order search to a leading-wildcard LIKE. Both defeat the index. This is the single most common cause of database slowness in production.

Where to look: APM → Databases, then Database Monitoring → Query Samples. Compare the explain plan before and after.
off

N+1 queries

Turns one batched join into roughly a hundred sequential round trips per request — the classic ORM lazy-loading pattern. Each query is fast; the request is not.

Where to look: APM → Traces. Open a /api/orders/recent trace and show the flame graph wall of mysql.query spans.
off

Connection pool exhaustion

Checkout holds its pooled connection open running real analytical aggregates. With a pool of 10 and concurrent traffic, requests queue for a connection and the whole storefront stalls.

Where to look: APM service page for __DEMO_NAME__-orders (latency spike, no matching DB time), then the pool readout on the storefront Insights tab.
off

Row-lock contention

Forces every checkout onto one hot SKU with SELECT … FOR UPDATE held open. Concurrent orders serialise behind a single row lock, and PostgreSQL picks up an idle-in-transaction session at the same time.

Where to look: Database Monitoring → Query Activity. Show sessions in lock wait and the blocking session tree.
off

Injected latency

Adds fixed delay at the BFF, ahead of any database work. Useful for showing that the trace tells you it is not the database — which is half of what observability is for.

Where to look: RUM → Performance, and the service map latency on __DEMO_NAME__-bff.
0 ms

Frontend error rate

Returns 503 for a percentage of storefront API calls, so RUM records real user-facing errors and failed sessions you can replay.

Where to look: RUM → Error Tracking, then open a Session Replay of a customer hitting the error.
0 %

Hold duration

How long the lock-contention and pool-exhaustion scenarios hold a connection or a row lock, doing genuine query work throughout. Four seconds is enough to be obvious without stalling the demo.

4 s

Order of play: show the slow query in DBM, read the explain plan, add the index here, refresh the storefront.
